# Plan Mode Guide

Plan Mode makes the AI create a structured plan before executing complex tasks, then execute it strictly after your approval. The plan is not advisory prose — it is **enforced at the code level**: machine validation before approval, scope gating and phase acceptance during execution, and automatic archiving on completion.

## Quick Start

```
/plan                 # Toggle plan mode
Describe your task... # AI analyzes the codebase and writes a plan document
                      # AI asks for approval via askuser
Select "Yes - Execute the entire plan"   # AI then executes all phases continuously
```

### Optional: clarify material decisions with Grill Me

The built-in `grill-me` skill resolves decisions that can materially change the implementation before plan approval. It inspects the codebase first, then asks exactly one `askuser` question at a time across scope, behavior, data shape, public APIs, compatibility, failure handling, testing, and hard-to-reverse architecture.

- Run `/skills-` in the input and select `grill-me`, then continue with the task description.
- The skill declares `disable-model-invocation: true`; it is injected only when the user selects it and never auto-triggers in ordinary conversation.
- Confirmed choices are recorded under `Resolved Decisions` in the draft. Clarification answers use `purpose: "clarification"` and **never count as execution approval**.
- Once decisions converge, the AI separately requests whole-plan approval with `purpose: "plan_approval"`.

### Recommended: persist plans with plan-manage (filesystem plan writes hard-blocked)

```js
// 1) Create a validatable draft once (prefer structured phases)
plan -
	manage({
		action: 'create',
		title: 'Task name',
		complexity: 'medium',
		acceptance_policy: 'strict',
		context: 'Why this change',
		phases: [
			{
				title: 'Implement',
				delivers: 'A runnable, verifiable vertical slice',
				executionStrategy: 'tdd',
				files: ['src/a.ts', 'src/b.ts (new)'],
				steps: ['Wire entrypoint', 'Add tests'],
				checks: [
					{type: 'command', command: 'pnpm test'},
					{type: 'diagnostics'},
					{type: 'manual', description: 'Verify the visible user flow'},
				],
				doneWhen: 'build passes; no diagnostic errors',
			},
		],
	});

// 2) Refine body before approval (keeps draft status)
plan -
	manage({
		action: 'write_body',
		phases: [
			/* updated phases */
		],
		analysis: '- **Affected files**: ...',
		risks: '...', // recommended for complex
	});
// After success, print the absolute plan path so the terminal can make it clickable
```

## Plan Lifecycle

Plan documents are created at `.snow/plan/YYYY-MM-DD/[task-name].md` (create-day folder), managed by a frontmatter state machine. Archive folders use the **archive day**, which may differ from the create day. Legacy top-level `.snow/plan/*.md` files are still discovered.

```
draft → executing (approved, advancing phase by phase) → completed → archived
                                                    ↘ abandoned → archived
```

- **Create**: use `plan-manage {action:"create", title, complexity, context?, phases?, analysis?, risks?, rollback?}`. Plans land under `.snow/plan/YYYY-MM-DD/` (create day). Prefer structured `phases` so Files/Steps/Done-when validate cleanly
- **Refine draft body**: `plan-manage {action:"write_body", phases? | body_markdown?, ...}` replaces the body while preserving draft/approved status (not for executing plans)
- **Approval**: after an explicit askuser approval, status becomes `executing` and the current phase is set to 1
- **Archiving**: once all phases pass final acceptance, the file is moved to `.snow/plan/archive/YYYY-MM-DD/` automatically (archive day; may differ from create day)
- **Abandon**: `plan-manage {action:"abandon", reason}` marks `abandoned` and archives the file
- **Fallback sweep**: leftover `completed` plans are archived automatically when plan mode is turned off

## Plan Document Format

Approval is machine-validated; this structure is mandatory:

```markdown
---
status: draft
current_phase: 0
created: 2026-07-25T00:00:00.000Z
session: <session id>
title: Task Name
complexity: simple # simple | medium | complex
acceptance_policy: strict # standard | strict
updated_at: 2026-07-25T00:00:00.000Z
---

# Task Name

## Analysis

- **Affected files**: files involved (mark files to be created with "(new)")

## Phases

### Phase 1: Name

- **Delivers**: an observable, acceptable vertical slice
- **Execution strategy**: tdd
- **Files**: src/a.ts
- **Steps**:
  - [ ] Step one
  - [ ] Step two
- **Checks**:
  - command: pnpm test
  - diagnostics
  - manual: verify the visible user flow
- **Done when**: build passes, no diagnostic errors
```

Validation rules (a failing plan is rejected; the AI receives a `[Plan Gate]` error and self-corrects):

| Rule                                         | Description                                                                        |
| -------------------------------------------- | ---------------------------------------------------------------------------------- |
| At least one `### Phase N`                   | Plans must be phased                                                               |
| Every phase has a `**Steps**` checklist      | Use `- [ ]` syntax                                                                 |
| Every phase has `**Done when**` criteria     | Concrete and verifiable                                                            |
| Referenced existing files must exist on disk | Prevents hallucinated paths; new files must be marked `(new)`                      |
| Complex plans need Risks or Rollback         | When `complexity: complex`, body must mention Risks/Rollback                       |
| TDD phases need a command Check              | `executionStrategy: tdd` cannot rely on manual checks alone                        |
| Check commands must pass the safety policy   | Compound shell, redirects, network, publish, and destructive commands are rejected |

Chinese labels `**文件**` / `**步骤**` / `**完成标准**` are recognized as well.

## Execution-Time Mechanics

### Per-Turn Progress Injection

After approval, every turn injects an "Active Plan" context: current phase, step check states, next step, Checks, acceptance policy, and Evidence path. This keeps the AI on-plan across long tasks.

### User-Visible Progress

- **StatusLine**: while Plan mode is on, shows a localized badge (`⚐ Plan` in English / `⚐ 计划` in Chinese); with an active plan it appends phase/step progress such as `⚐ Plan P1/3 · 2/5`. Draft shows a localized status word (e.g. `Draft` / `草稿`), not the raw English frontmatter token only. Frontmatter status values stay English for the state machine.
- **Approval preview**: when askuser asks to approve/continue a plan, a compact summary (phases, files, steps, Checks, acceptance policy, and Evidence path) is rendered above the options, making every command visible before execution.

### The plan-manage Tool

During execution the AI maintains plan state through the built-in `plan-manage` tool:

| action           | Purpose                                                                                                                                                                               |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `create`         | Scaffold a draft plan under today's date folder (`title` required; optional `complexity`, `context`, `slug`, structured `phases`, `analysis`, `risks`, `rollback`)                    |
| `write_body`     | Replace draft/approved plan body via `body_markdown` and/or structured `phases` (+ optional context/analysis/risks/rollback); **does not** change status/session/current_phase        |
| `get` / `status` | Summarize active plan progress for this session                                                                                                                                       |
| `list`           | List all active plans (all sessions) under `.snow/plan`                                                                                                                               |
| `check_step`     | Check off a step right after finishing it                                                                                                                                             |
| `uncheck_step`   | Unmark a step (optional `phase_index`)                                                                                                                                                |
| `complete_phase` | Checks Files scope, manual confirmations, phase Checks, build, and IDE diagnostics; writes Evidence and **only advances when all pass**; failed attempts are retained                 |
| `amend`          | Revise the plan: append Files/Steps to a phase with a recorded reason, refreshing the write allowlist                                                                                 |
| `complete`       | Final acceptance + automatic archiving                                                                                                                                                |
| `abandon`        | Drop the active plan (`reason` required); status `abandoned` + archive                                                                                                                |
| `adopt`          | Rebind an executing plan to this session and restore the gate; require `plan_path` when multiple plans exist; live foreign takeover needs `force:true` + `reason`                     |
| `archive_batch`  | Batch-archive active plans; defaults to **current session only** and statuses `draft/completed/abandoned` (**protects executing**); `scope=all` and `include_executing` need `reason` |

Acceptance is configurable via `planAcceptance` in `.snow/settings.json`:

```json
{
	"planAcceptance": {
		"commands": ["pnpm run build"],
		"runBuild": true,
		"runDiagnostics": true,
		"preferPackageManager": "pnpm",
		"fallbackCommands": ["pnpm test"],
		"allowedCommandPrefixes": ["pnpm", "npm"],
		"commandTimeoutMs": 120000,
		"policy": "strict"
	}
}
```

- `policy` is `standard` or `strict`. A plan's frontmatter `acceptance_policy` takes precedence over project settings.
- `standard` may skip when no build command is discoverable or no IDE is connected. `strict` fails closed for a missing build, unavailable diagnostics, unavailable Git baseline, or missing phase baseline.
- `allowedCommandPrefixes` restricts phase command Check prefixes; `commandTimeoutMs` sets the timeout for each acceptance command.
- Command Checks reject shell composition, redirects, command substitution, nested shells, directory changes, network requests, publishing, destructive Git operations, and file deletion. Split multiple checks into separate `command` entries.

Auto-detect (when `commands` is omitted):

- If `package.json` has `scripts.build`, the package manager is chosen from lockfiles (`pnpm-lock.yaml` → pnpm, `yarn.lock` → yarn, `bun.lockb`/`bun.lock` → bun, `package-lock.json` → npm; default npm).
- When no lockfile is present, optional `preferPackageManager` (`npm` | `pnpm` | `yarn` | `bun`) is used.
- Optional `fallbackCommands` run only when there is no build script and no explicit `commands` (test/typecheck are **not** auto-run unless you set them here).
- Non-Node markers (`Cargo.toml` / `go.mod` / `pyproject.toml`) soft-skip with a hint to set `planAcceptance.commands` (no auto `cargo build` / `go build`).
- Projects without a build script skip the build check (not a failure); diagnostics are skipped when no IDE is connected. Diagnostics prefer structured JSON severity (`error` / `Error` / `1`) with regex fallback.

### JSON Acceptance Evidence

Every `complete_phase` attempt is appended to `<plan>.md.evidence.json`; passed and failed attempts are both retained, up to the latest 500 entries. Each entry includes the phase, timestamps, duration, command/diagnostics/build/manual results, exit codes, manual confirmations, Git-changed files, and out-of-scope files.

Evidence uses atomic replacement and a per-plan write queue. If Evidence cannot be written, the phase is not accepted. Archiving moves the sidecar together with the Markdown plan, resolves name collisions as a pair, and attempts to roll back the plan move if the Evidence move fails.

### Scope Gating (planStrictness)

After approval, file writes are checked against the **current phase's Files allowlist**. Configure via `planStrictness` in the project's `.snow/settings.json`:

| Value            | Behavior                                                                         |
| ---------------- | -------------------------------------------------------------------------------- |
| `soft` (default) | Out-of-plan writes are allowed but a warning is injected asking to `amend` first |
| `strict`         | Out-of-plan writes are blocked; `amend` is required first                        |
| `off`            | No checking                                                                      |

After approval, `.snow/plan/**` and `.trellis/tasks/**` remain always in scope. While unapproved: filesystem write tools may target `.trellis/tasks/**` only; filesystem writes under `.snow/plan/**` are hard-blocked — use `plan-manage` instead.

In `strict` (and warning-only in `soft`), the gate also inspects **obvious shell write targets** extracted from `terminal-execute` commands — redirects (`>` / `>>`), destructive commands (`rm`/`del`/`mv`/`cp`/`sed -i`), and common PowerShell writers (`Set-Content`/`Out-File`/`New-Item`). Pure build/test commands such as `npm run build` are allowed when no clear write path can be extracted. Heuristics are conservative: if no path is found, the command is allowed.

### Pre-Approval Hard Gate

Before approval, the AI can only read/search code and write plan documents via **`plan-manage`**. Business file writes, **all terminal commands** (`terminal-execute` is hard-blocked — including IDE CLI open helpers), and writable sub-agents are rejected at the tool layer — even YOLO mode cannot bypass this. While unapproved, `filesystem-create` / `filesystem-edit` / `filesystem-replaceedit` targeting `.snow/plan/**` are **hard-blocked** by the gate (with a plan-manage guidance message); `.trellis/tasks/**` filesystem writes remain allowed. After creating a plan file, print its absolute path on its own line so the terminal can make it clickable; do not attempt IDE open via shell until the plan is approved.

## Resume Support and Cross-Process Isolation

After a session resume (`/resume`), if this session still owns an `executing` plan and can acquire the repo owner lock, gate approval is restored from disk so execution can continue.

Rules for one working tree (one `.snow/plan` root):

- **Multiple drafts may coexist**; **only one live executing owner** is allowed at a time
- Owner lock path: `.snow/plan/.runtime/owner.lock.json` (scoped by cwd/worktree; separate clones/worktrees are independent)
- Ownership is classified as: `mine_active` / `mine_recoverable` / `foreign_live` / `foreign_soft_stale` / `foreign_hard_stale` / `untagged_recoverable`
- When unfinished plans from other sessions are found, the model gets an explicit list (path/session/phase/ownership/lock) and **must not silently adopt the newest plan**
- Resume requires an explicit call: `plan-manage {action:"adopt", plan_path:"..."}`
- Taking over a **live** or **soft-stale** foreign owner requires `force:true` plus a non-empty `reason` (written as a takeover note). Soft-stale **never** auto-adopts without force.
- Crash leftovers (dead pid, or unknown/remote past the hard-stale window) can be recovered without force
- Generic Continue/approve answers never rebind ownership themselves — they route to `plan-manage adopt`
- Concurrent plan-file writes use `updated_at` / `mtime` CAS; conflicts require reload + retry
- `archive_batch` defaults to `scope=session` (only plans whose `frontmatter.session` matches the current session); `scope=all` requires `reason`
- Project-level `planMode` remains shared in `.snow/settings.json`; for true parallel edits use separate worktrees/clones

### Hard Rules (must not break)

1. **Visibility ≠ ownership**: `list` / resume notices may show other sessions' plans without granting mutation rights
2. **Live hard owners are not stealable by default**: `foreign_live` rejects Continue / no-force adopt / headless resume
3. **Soft-stale only upgrades the prompt — it is never auto-equivalent to hard-stale**: old heartbeat with a live pid still needs `force+reason`
4. **Continue ≠ force takeover**: interactive Continue never silently steals a lock
5. **soft-stale / live require force+reason to adopt**
6. **Interactive Continue**: only unique recoverable kinds (`mine_recoverable` / `untagged_recoverable` / `foreign_hard_stale`) may adopt without force (still via `plan-manage adopt`)
7. **Headless: live foreign fails by default**; optional `forceTakeover+forceReason` for explicit takeover

### Ownership isolation matrix

| Scenario                                   | ownership              | Visible in list | Continue / adopt without force | force+reason adopt | New plan approve | Headless `--plan-file`                          |
| ------------------------------------------ | ---------------------- | --------------- | ------------------------------ | ------------------ | ---------------- | ----------------------------------------------- |
| This session executing (live lock)         | `mine_active`          | yes             | n/a (already owned)            | optional refresh   | Continue running | allowed                                         |
| This session interrupted (no/dead lock)    | `mine_recoverable`     | yes             | Yes (via adopt)                | optional           | Adopt first      | allowed                                         |
| Untagged executing plan                    | `untagged_recoverable` | yes             | Yes (via adopt)                | optional           | Hint             | allowed                                         |
| Foreign session dead / remote hard-expired | `foreign_hard_stale`   | yes             | Yes (via adopt)                | optional           | Hint to clean up | allowed                                         |
| Foreign session pid alive, heartbeat old   | `foreign_soft_stale`   | yes             | **No**                         | **Required**       | **Hard block**   | fails by default; optional forceTakeover+reason |
| Foreign session alive, heartbeat fresh     | `foreign_live`         | yes             | **No**                         | **Required**       | **Hard block**   | fails by default; optional forceTakeover+reason |

Target behavior cheat sheet:

| Scenario                                                | Expected                                           |
| ------------------------------------------------------- | -------------------------------------------------- |
| A live, B Continue / approve new plan / headless resume | **block**                                          |
| A dead (hard-stale), B adopt / headless resume          | **allowed without force**                          |
| soft-stale                                              | **requires force+reason**                          |
| mine recoverable / same-session restore                 | **restore / adopt without force**                  |
| Continue with multiple plans                            | explicit `plan_path` / `Continue: <path>` required |

Notes:

- **soft-stale never auto-adopts without force** — the pid is still alive; only the heartbeat is old.
- Approving a **new plan** hard-blocks only when `foreign_live` / `foreign_soft_stale` exists; hard-stale leftovers are not hard-blocked (optional cleanup).
- A generic askuser "Continue this plan" answer never takes over a live/soft-stale foreign owner; it always requires `plan-manage adopt` (with force+reason when needed).

### Headless Mode

Headless (`--ask`) does **not** support interactive `askuser` plan approval. Default remains `planMode=false`.

Opt-in resume only:

- `--plan-file <path>` — resume a specific `approved`/`executing` plan without askuser, **only when ownership allows non-force adopt** (same session, hard-stale foreign, untagged recoverable)
- `--plan` or `--yolo-p` with `--ask` — restore gate only when this session already has an executing plan on disk and can acquire the owner lock
- **Live / soft-stale foreign plans fail by default** — headless never silently force-adopts
- Optional programmatic takeover: `tryResumeHeadlessPlan({ planFile, forceTakeover: true, forceReason: "..." })` (or the equivalent headless API). `forceTakeover` without `forceReason` still fails; success writes a takeover note
- If opt-in cannot restore a preapproved plan, plan mode stays off (safe: do not enter an unapproved hard gate with no interactive unlock)

Recommended takeover flow:

1. `plan-manage {action:"list"}` to confirm `ownership=` and lock liveness
2. Prefer letting the live owner `complete` / `abandon`
3. If takeover is intentional: interactive `plan-manage {action:"adopt", plan_path, force:true, reason}`; headless uses `forceTakeover+forceReason`
4. Resume from the first unchecked step of the current phase

`plan-manage` non-interactive actions (`check_step`, `complete_phase`, `complete`, `abandon`, `adopt`, …) still work once the gate is approved.

### Telemetry

When OpenTelemetry is enabled, plan lifecycle events are emitted best-effort:

- `snow.plan.approve` — gate approved (askuser success or headless resume)
- `snow.plan.complete_phase` / `snow.plan.complete` / `snow.plan.abandon`
- `snow.plan.gate_block` / `snow.plan.scope_warning`

Common attributes: `snow.plan.status`, `snow.plan.phase`, `snow.plan.strictness`, `snow.tool.name`, `snow.mode.plan`.

## FAQ

**Q: The AI says "plan approved" but tools are still blocked?**
Approval must come from an explicit `askuser-ask_question` option (e.g. "Yes - Execute the entire plan"). Plain chat replies do not unlock the gate.

**Q: Approval rejected with missing_file?**
The plan references a non-existent file path. Fix the path, or mark newly created files with `(new)`.

**Q: Need to edit a file outside the plan?**
Have the AI call `plan-manage {action: "amend"}` to add it to the plan first (under `soft` mode a direct edit also works, but triggers a warning).

**Q: Where do active plans live? Where are archived plans?**
Active plans live at `.snow/plan/YYYY-MM-DD/[task-name].md` (create-day folder); legacy top-level `.snow/plan/*.md` files are still discovered. Archives go to `.snow/plan/archive/YYYY-MM-DD/`, grouped by **archive date** (may differ from create date); name collisions get a `-2` suffix.

**Q: Why can't I use `filesystem-create` for plan files?**
While unapproved, the tool gate **hard-blocks** `filesystem-create` / `filesystem-edit` / `filesystem-replaceedit` under `.snow/plan/**` and steers you to `plan-manage` (`create` / `write_body` / `amend`). Freeform filesystem writes have produced empty `filePath: []` failures and broken frontmatter; plan-manage is the only supported persist path. Print the absolute path after create/write_body so the terminal can make it clickable.
