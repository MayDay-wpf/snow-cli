# 计划模式指南

计划模式(Plan Mode)让 AI 在执行复杂任务前先制定结构化计划,经你批准后再严格按计划执行。计划不是一段"仅供参考"的文字——它由**代码层强制**:批准前有机器校验,执行期有范围门控和阶段验收,完成后自动归档。

## 快速开始

```
/plan                 # 切换计划模式
描述你的任务...        # AI 分析代码库并生成计划文档
                      # AI 通过 askuser 询问是否批准
选择"Yes - Execute the entire plan"   # 批准后 AI 连续执行所有阶段
```

### 推荐：用 plan-manage 落盘计划（工具层硬拦截 filesystem 写计划）

```js
// 1) 一次创建可校验的草稿（优先结构化 phases）
plan -
	manage({
		action: 'create',
		title: '任务名',
		complexity: 'medium',
		context: '为什么要做',
		phases: [
			{
				title: '实现',
				files: ['src/a.ts', 'src/b.ts (new)'],
				steps: ['改入口', '补测试'],
				doneWhen: '构建通过，无诊断错误',
			},
		],
	});

// 2) 批准前继续补全文（保留 draft 状态）
plan -
	manage({
		action: 'write_body',
		phases: [
			/* 更新后的阶段 */
		],
		analysis: '- **Affected files**: ...',
		risks: '...', // complex 建议提供
	});
// 成功后打印计划文件的绝对路径，方便终端点击打开
```

## 计划生命周期

计划文档创建于 `.snow/plan/YYYY-MM-DD/[任务名].md`（创建日目录），由 frontmatter 状态机管理。归档目录按**归档日**存放，可能与创建日不同。旧的顶层 `.snow/plan/*.md` 仍可被发现。

```
draft(草稿) → executing(批准执行中,逐阶段推进) → completed(完成) → archived(归档)
                                              ↘ abandoned(放弃) → archived
```

- **创建**:使用 `plan-manage {action:"create", title, complexity, context?, phases?, analysis?, risks?, rollback?}`。计划写入 `.snow/plan/YYYY-MM-DD/`（创建日）。优先传结构化 `phases`，便于 Files/Steps/Done-when 通过校验
- **修订草稿正文**:`plan-manage {action:"write_body", phases? | body_markdown?, ...}` 只替换正文，保留 draft/approved 状态（不可用于 executing）
- **批准**:通过 askuser 明确批准后,状态变为 `executing`,当前阶段置为 1
- **归档**:全部阶段完成并通过最终验收后,文件自动移入 `.snow/plan/archive/YYYY-MM-DD/`（归档日，可能与创建日不同）
- **放弃**:`plan-manage {action:"abandon", reason}` 标记 `abandoned` 并归档
- **兜底清扫**:关闭计划模式时,遗留的 `completed` 计划会被自动归档

## 计划文档格式

批准时会做机器校验,以下结构是强制的:

```markdown
---
status: draft
current_phase: 0
created: 2026-07-25T00:00:00.000Z
session: <会话 ID>
title: 任务名
complexity: simple # simple | medium | complex
updated_at: 2026-07-25T00:00:00.000Z
---

# 任务名

## Analysis

- **Affected files**: 涉及的文件(新建文件标注 "(new)")

## Phases

### Phase 1: 阶段名

- **Files**: src/a.ts
- **Steps**:
  - [ ] 步骤一
  - [ ] 步骤二
- **Done when**: 构建通过,无诊断错误
```

校验规则(不满足则批准被拒,AI 会收到 `[Plan Gate]` 错误并自我修正):

| 规则                              | 说明                                                 |
| --------------------------------- | ---------------------------------------------------- |
| 至少 1 个 `### Phase N`           | 计划必须分阶段                                       |
| 每阶段有 `**Steps**` 勾选清单     | 用 `- [ ]` 语法                                      |
| 每阶段有 `**Done when**` 验收标准 | 具体、可验证                                         |
| 引用的已有文件必须真实存在        | 防止幻觉路径;新建文件需标注 `(new)`                  |
| complex 计划需 Risks/Rollback     | `complexity: complex` 时正文须包含 Risks 或 Rollback |

中文标签 `**文件**` / `**步骤**` / `**完成标准**` 同样被识别。

## 执行期机制

### 每轮进度注入

批准后,每轮对话会自动注入"Active Plan"上下文:当前阶段、步骤勾选状态、下一步、验收标准。这确保长任务中 AI 不会偏离计划。

### 用户可见进度

- **StatusLine**: Plan 开启时显示本地化徽章（中文为 `⚐ 计划`）；若有活跃计划会附加阶段/步骤进度，例如执行中 `⚐ 计划 P1/3 · 2/5`，草稿为 `⚐ 计划 (草稿) · 2 个阶段`（英文仍为 `Draft` / `phase(s)`）。frontmatter 机读状态保持英文。
- **批准预览**: 当 askuser 询问批准/继续计划时，在选项上方自动渲染当前计划文档摘要（阶段、文件、步骤），无需手动打开文件。

### plan-manage 工具

AI 在执行期通过内置工具 `plan-manage` 维护计划状态:

| action           | 作用                                                                                                                                               |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `create`         | 按模板创建草稿计划到今日日期目录（必填 `title`；可选 `complexity`/`context`/`slug`、结构化 `phases`、`analysis`/`risks`/`rollback`）               |
| `write_body`     | 用 `body_markdown` 和/或结构化 `phases`（及可选 context/analysis/risks/rollback）替换 draft/approved 正文；**不改变** status/session/current_phase |
| `get` / `status` | 查看本会话活跃计划进度                                                                                                                             |
| `list`           | 列出 `.snow/plan` 下全部活跃计划（跨会话）                                                                                                         |
| `check_step`     | 完成一个步骤后立即勾选                                                                                                                             |
| `uncheck_step`   | 取消勾选步骤（可选 `phase_index`）                                                                                                                 |
| `complete_phase` | 阶段验收:运行可配置构建命令 + IDE 诊断检查,**通过才推进**到下一阶段;失败则返回错误输出要求修复                                                     |
| `amend`          | 修订计划:向阶段追加 Files/Steps 并记录原因,同时刷新写入白名单                                                                                      |
| `complete`       | 最终验收 + 自动归档                                                                                                                                |
| `abandon`        | 放弃活跃计划（必填 `reason`）；标记 `abandoned` 并归档                                                                                             |
| `adopt`          | 将执行中的计划重绑到本会话并恢复门控；多计划时必填 `plan_path`；接管存活外会话需 `force:true` + `reason`                                           |
| `archive_batch`  | 批量归档活跃计划；默认**仅本会话**、状态 `draft/completed/abandoned`，**不伤 executing**；`scope=all` 与 `include_executing` 均需 `reason`         |

验收可通过 `.snow/settings.json` 的 `planAcceptance` 配置：

```json
{
	"planAcceptance": {
		"commands": ["pnpm run build"],
		"runBuild": true,
		"runDiagnostics": true,
		"preferPackageManager": "pnpm",
		"fallbackCommands": ["pnpm test"]
	}
}
```

自动探测（未配置 `commands` 时）：

- 若 `package.json` 存在 `scripts.build`，按锁文件选择包管理器（`pnpm-lock.yaml` → pnpm、`yarn.lock` → yarn、`bun.lockb`/`bun.lock` → bun、`package-lock.json` → npm；默认 npm）。
- 无锁文件时，可用可选字段 `preferPackageManager`（`npm` | `pnpm` | `yarn` | `bun`）。
- 可选 `fallbackCommands`：仅在没有 build 脚本且未配置 `commands` 时运行（默认不会自动跑 test/typecheck，除非你在此显式配置）。
- 非 Node 标记（`Cargo.toml` / `go.mod` / `pyproject.toml`）会 soft-skip，并提示配置 `planAcceptance.commands`（不会默认执行 `cargo build` / `go build`）。
- 无 build 脚本的项目会跳过构建检查（不算失败）；IDE 未连接时跳过诊断检查。诊断优先解析结构化 JSON 的 severity（`error` / `Error` / `1`），失败时回退正则。

### 范围门控(planStrictness)

批准后,AI 写文件时会检查目标是否在**当前阶段的 Files 白名单**内。通过项目 `.snow/settings.json` 的 `planStrictness` 配置:

| 值           | 行为                                             |
| ------------ | ------------------------------------------------ |
| `soft`(默认) | 计划外写入放行,但注入警告要求先 `amend` 修订计划 |
| `strict`     | 计划外写入直接阻断,必须先 `amend`                |
| `off`        | 不检查                                           |

批准后，`.snow/plan/**` 与 `.trellis/tasks/**` 仍在 scope 内始终可写。未批准时：`.trellis/tasks/**` 可用 filesystem 写工具；`.snow/plan/**` 的 filesystem 写被硬拦截，只能走 `plan-manage`。

在 `strict`（`soft` 仅警告）下，门控还会检查 `terminal-execute` 中**可明确提取的 shell 写目标**：重定向（`>` / `>>`）、破坏性命令（`rm`/`del`/`mv`/`cp`/`sed -i`）、常见 PowerShell 写入（`Set-Content`/`Out-File`/`New-Item`）。像 `npm run build` 这类纯构建/测试命令在无法提取写路径时放行。启发式保守：提取不到路径则放行，避免误杀。

### 批准前硬门控

批准前,AI 只能读代码/搜索，并通过 **`plan-manage`** 写计划文档。业务文件写入、**全部终端命令**（`terminal-execute` 硬阻断，包括用 IDE CLI 打开计划文件）、可写子代理全部被工具层拒绝——即使 YOLO 模式也无法绕过。未批准时，`filesystem-create` / `filesystem-edit` / `filesystem-replaceedit` 写 `.snow/plan/**` 会被 gate **硬拦截**（返回 plan-manage 引导）；`.trellis/tasks/**` 仍允许 filesystem 写入。创建计划文件后应把绝对路径单独打印一行，依赖终端可点击路径打开；在计划获批前不要尝试 shell 打开 IDE。

## 断点续跑与跨进程隔离

会话恢复(`/resume`)后，若本会话仍有 `executing` 计划且能拿到仓库级 owner lock，门控会从磁盘恢复，执行可继续。

同一工作树（同一 `.snow/plan`）规则：

- **多个 draft 可并行**；**同一时刻只允许一个 live executing owner**
- Owner lock 文件：`.snow/plan/.runtime/owner.lock.json`（按 cwd/worktree 隔离；不同 clone/worktree 互不影响）
- 所有权分类：`mine_active` / `mine_recoverable` / `foreign_live` / `foreign_soft_stale` / `foreign_hard_stale` / `untagged_recoverable`
- 新会话发现其它会话的 unfinished 计划时，会注入列表（路径/session/phase/ownership/lock），**禁止静默 adopt 最新一个**
- 继续必须显式：`plan-manage {action:"adopt", plan_path:"..."}`
- 接管 **live** 或 **soft-stale** 外会话 owner：`force:true` + 非空 `reason`（写入 takeover 笔记）。soft-stale **永不**无 force 自动接管
- 崩溃残留（pid 已死或远程/未知且超过 hard-stale 窗口）可无 force 恢复
- 通用 Continue/批准回答本身不会重绑所有权，一律走 `plan-manage adopt`
- 计划文件写冲突：`updated_at` / `mtime` CAS 失败会要求 reload 后重试
- `archive_batch` 默认 `scope=session`（仅 `frontmatter.session` 匹配当前会话）；`scope=all` 必须带 `reason`
- 项目级 `planMode` 开关仍共享于 `.snow/settings.json`；真正并行改代码请用独立 worktree/clone

### 关键规则（不可破）

1. **可见性 ≠ 所有权**：`list` / 预处理器能看到其它会话的计划，不等于可以 mutate
2. **live hard owner 默认不可抢**：`foreign_live` 默认拒绝 Continue / 无 force adopt / 无头 resume
3. **soft-stale 只升级提示，不自动等价 hard-stale**：心跳过期但 pid 仍存活时仍需 `force+reason`
4. **Continue ≠ force takeover**：交互 Continue 不会静默抢锁
5. **soft-stale / live 必须 force+reason 才能 adopt**
6. **交互 Continue**：仅 unique recoverable（`mine_recoverable` / `untagged_recoverable` / `foreign_hard_stale`）允许无 force adopt（仍走 `plan-manage adopt`）
7. **headless：live foreign 默认失败**；可选 `forceTakeover+forceReason` 显式接管

### 所有权隔离矩阵

| 场景                             | ownership              | list 可见 | Continue/adopt 无 force | force+reason adopt | 新计划 approve | headless `--plan-file`              |
| -------------------------------- | ---------------------- | --------- | ----------------------- | ------------------ | -------------- | ----------------------------------- |
| 本 session 执行中（锁活）        | `mine_active`          | 是        | n/a（已拥有）           | 可选刷新           | 续跑           | 允许                                |
| 本 session 中断（无锁/死锁）     | `mine_recoverable`     | 是        | 是（经 adopt）          | 可选               | 先 adopt       | 允许                                |
| untagged executing               | `untagged_recoverable` | 是        | 是（经 adopt）          | 可选               | 提示           | 允许                                |
| 外 session 已死 / 跨机 hard 过期 | `foreign_hard_stale`   | 是        | 是（经 adopt）          | 可选               | 提示清理       | 允许                                |
| 外 session pid 存活，心跳偏旧    | `foreign_soft_stale`   | 是        | **否**                  | **必须**           | **硬拦**       | 默认失败；可选 forceTakeover+reason |
| 外 session 存活，心跳新鲜        | `foreign_live`         | 是        | **否**                  | **必须**           | **硬拦**       | 默认失败；可选 forceTakeover+reason |

目标行为速查：

| 场景                                              | 期望                                      |
| ------------------------------------------------- | ----------------------------------------- |
| A live，B Continue / 批准新计划 / headless resume | **block**                                 |
| A dead（hard-stale），B adopt / headless resume   | **允许无 force**                          |
| soft-stale                                        | **必须 force+reason**                     |
| mine 可恢复 / 同会话 restore                      | **restore / adopt 无 force**              |
| 多计划 Continue                                   | 必须显式 `plan_path` / `Continue: <path>` |

说明：

- **soft-stale 永不无 force 自动 adopt**——pid 仍活着，只是心跳偏旧。
- 批准**新计划**时，仅当存在 `foreign_live` / `foreign_soft_stale` 才硬拦；hard-stale 残留不硬拦（可选清理）。
- askuser 通用「继续该计划」绝不会接管 live/soft-stale 外会话；一律要求 `plan-manage adopt`（需要时 force+reason）。

- **允许** = 默认成功路径

- **需 force+reason** = 仅 `adopt force:true` + 非空 `reason`（或 headless `forceTakeover+forceReason`）

| headless `--plan` 同 session       | 允许                | 允许                              | n/a                          | n/a                          |
| headless `--plan-file`             | 允许                | **允许无 force**                  | **默认失败**                 | **默认失败**                 |
| headless forceTakeover+reason      | n/a                 | 可选                              | **允许**                     | **允许**                     |
| `buildResumePlanNotice`            | 不弹（已有 active） | 提示 Continue                     | 提示僵尸+force               | 提示勿并行+force             |

#### Owner lock 语义速查

| 条件                                  | liveness          | 典型 ownership         | 无 force 接管      |
| ------------------------------------- | ----------------- | ---------------------- | ------------------ |
| 同 session + 本 pid + 心跳新鲜        | live              | `mine_active`          | 已是 owner         |
| 本 session，锁缺失/pid 死             | hard-stale / none | `mine_recoverable`     | **是**             |
| 外 session，pid 活 + 心跳 ≤12min      | live              | `foreign_live`         | **否**             |
| 外 session，pid 活 + 心跳 >12min      | soft-stale        | `foreign_soft_stale`   | **否**（要 force） |
| 外 session，pid 死；或跨机心跳 >30min | hard-stale        | `foreign_hard_stale`   | **是**             |
| 无 session 标签的 executing           | —                 | `untagged_recoverable` | **是**             |

### 无头模式

无头（`--ask`）**不支持**通过 `askuser` 交互式批准计划。默认仍为 `planMode=false`。

仅支持 opt-in 续跑：

- `--plan-file <path>` — 无 askuser 恢复指定 `approved`/`executing` 计划，**仅当所有权允许无 force adopt**（本会话、hard-stale 外会话、untagged 可恢复）
- `--plan` 或 `--yolo-p` 配合 `--ask` — 仅当本会话磁盘上已有 executing 计划且能拿到 owner lock 时恢复门控
- **live / soft-stale 外会话计划默认拒绝**——无头不会静默 force adopt
- 可选程序化接管：`tryResumeHeadlessPlan({ planFile, forceTakeover: true, forceReason: "..." })`（或等价 headless API）。缺少 `forceReason` 时仍失败；成功时写入 takeover 笔记
- 若 opt-in 无法恢复预批准计划，则保持 plan 关闭（安全：避免进入无法交互解锁的未批准硬门控）

推荐接管流程：

1. `plan-manage {action:"list"}` 确认 `ownership=` 与 lock 状态
2. 优先让 live owner 自行 `complete` / `abandon`
3. 确认需要接管时：交互 `plan-manage {action:"adopt", plan_path, force:true, reason}`；无头则 `forceTakeover+forceReason`
4. 接管后从当前 phase 第一个未勾选步骤继续

门控已批准后，`plan-manage` 的非交互动作（`check_step` / `complete_phase` / `complete` / `abandon` / `adopt` 等）仍可正常使用。

### 遥测

启用 OpenTelemetry 时，计划生命周期事件会尽力上报：

- `snow.plan.approve` — 门控批准（askuser 成功或无头续跑）
- `snow.plan.complete_phase` / `snow.plan.complete` / `snow.plan.abandon`
- `snow.plan.gate_block` / `snow.plan.scope_warning`

常见属性：`snow.plan.status`、`snow.plan.phase`、`snow.plan.strictness`、`snow.tool.name`、`snow.mode.plan`。

## 常见问题

**Q: AI 说"计划已批准"但工具仍被拦截?**
批准必须通过 `askuser-ask_question` 的明确选项(如 "Yes - Execute the entire plan"、"批准并执行"、"继续执行"),普通聊天回复不会解锁门控。

**Q: 批准被拒绝提示 missing_file?**
计划里引用了不存在的文件路径。修正路径,或给计划新建的文件加 `(new)` 标注。

**Q: 想临时改计划外的文件?**
让 AI 先调用 `plan-manage {action: "amend"}` 把文件加进计划(soft 模式下直接改也可以,但会收到警告)。

**Q: 活跃计划写在哪? 归档的计划在哪?**
活跃计划在 `.snow/plan/YYYY-MM-DD/[任务名].md`（创建日目录）；旧的顶层 `.snow/plan/*.md` 仍可被发现。归档在 `.snow/plan/archive/YYYY-MM-DD/`，按**归档日**分目录（可与创建日不同），重名自动加 `-2` 后缀。

**Q: 为什么不能用 `filesystem-create` 写计划文件?**
未批准时工具层会**硬拦截**对 `.snow/plan/**` 的 `filesystem-create` / `filesystem-edit` / `filesystem-replaceedit`，并引导改用 `plan-manage`（`create` / `write_body` / `amend`）。自由 filesystem 写曾导致空 `filePath: []` 失败和 frontmatter 损坏；plan-manage 是唯一落盘路径。create/write_body 后打印绝对路径，方便终端一键打开。
