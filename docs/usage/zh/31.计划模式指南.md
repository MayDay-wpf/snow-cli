# 计划模式指南

计划模式(Plan Mode)让 AI 在执行复杂任务前先制定结构化计划,经你批准后再严格按计划执行。计划不是一段"仅供参考"的文字——它由**代码层强制**:批准前有机器校验,执行期有范围门控和阶段验收,完成后自动归档。

## 快速开始

```
/plan                 # 切换计划模式
描述你的任务...        # AI 分析代码库并生成计划文档
                      # AI 通过 askuser 询问是否批准
选择"Yes - Execute the entire plan"   # 批准后 AI 连续执行所有阶段
```

## 计划生命周期

计划文档创建于 `.snow/plan/YYYY-MM-DD/[任务名].md`（创建日目录），由 frontmatter 状态机管理。归档目录按**归档日**存放，可能与创建日不同。旧的顶层 `.snow/plan/*.md` 仍可被发现。

```
draft(草稿) → executing(批准执行中,逐阶段推进) → completed(完成) → archived(归档)
                                              ↘ abandoned(放弃) → archived
```

- **创建**:优先 `plan-manage {action:"create", title, complexity}`（也可用 filesystem-create）。计划写入 `.snow/plan/YYYY-MM-DD/`（创建日）；顶层写入会自动重定向
- **批准**:通过 askuser 明确批准后,状态变为 `executing`,当前阶段置为 1
- **归档**:全部阶段完成并通过最终验收后,文件自动移入 `.snow/plan/archive/YYYY-MM-DD/`（归档日，可能与创建日不同）
- **放弃**:`plan-manage {action:"abandon", reason}` 标记 `abandoned` 并归档
- **兜底清扫**:关闭计划模式时,遗留的 `completed` 计划会被自动归档

## 计划文档格式

批准时会做机器校验,以下结构是强制的:

```markdown
---
status: draft
current_phase: 0
created: 2026-07-25T00:00:00.000Z
session: <会话 ID>
title: 任务名
complexity: simple # simple | medium | complex
updated_at: 2026-07-25T00:00:00.000Z
---

# 任务名

## Analysis

- **Affected files**: 涉及的文件(新建文件标注 "(new)")

## Phases

### Phase 1: 阶段名

- **Files**: src/a.ts
- **Steps**:
  - [ ] 步骤一
  - [ ] 步骤二
- **Done when**: 构建通过,无诊断错误
```

校验规则(不满足则批准被拒,AI 会收到 `[Plan Gate]` 错误并自我修正):

| 规则                              | 说明                                                 |
| --------------------------------- | ---------------------------------------------------- |
| 至少 1 个 `### Phase N`           | 计划必须分阶段                                       |
| 每阶段有 `**Steps**` 勾选清单     | 用 `- [ ]` 语法                                      |
| 每阶段有 `**Done when**` 验收标准 | 具体、可验证                                         |
| 引用的已有文件必须真实存在        | 防止幻觉路径;新建文件需标注 `(new)`                  |
| complex 计划需 Risks/Rollback     | `complexity: complex` 时正文须包含 Risks 或 Rollback |

中文标签 `**文件**` / `**步骤**` / `**完成标准**` 同样被识别。

## 执行期机制

### 每轮进度注入

批准后,每轮对话会自动注入"Active Plan"上下文:当前阶段、步骤勾选状态、下一步、验收标准。这确保长任务中 AI 不会偏离计划。

### plan-manage 工具

AI 在执行期通过内置工具 `plan-manage` 维护计划状态:

| action           | 作用                                                                                           |
| ---------------- | ---------------------------------------------------------------------------------------------- |
| `create`         | 按模板创建草稿计划到今日日期目录（必填 `title`；可选 `complexity`/`context`/`slug`）           |
| `get` / `status` | 查看本会话活跃计划进度                                                                         |
| `list`           | 列出 `.snow/plan` 下全部活跃计划（跨会话）                                                     |
| `check_step`     | 完成一个步骤后立即勾选                                                                         |
| `uncheck_step`   | 取消勾选步骤（可选 `phase_index`）                                                             |
| `complete_phase` | 阶段验收:运行可配置构建命令 + IDE 诊断检查,**通过才推进**到下一阶段;失败则返回错误输出要求修复 |
| `amend`          | 修订计划:向阶段追加 Files/Steps 并记录原因,同时刷新写入白名单                                  |
| `complete`       | 最终验收 + 自动归档                                                                            |
| `abandon`        | 放弃活跃计划（必填 `reason`）；标记 `abandoned` 并归档                                         |
| `adopt`          | 将执行中的计划重绑到本会话并恢复门控（可选 `plan_path`）                                       |

验收可通过 `.snow/settings.json` 的 `planAcceptance` 配置：

```json
{
	"planAcceptance": {
		"commands": ["npm run build"],
		"runBuild": true,
		"runDiagnostics": true
	}
}
```

无 build 脚本的项目会跳过构建检查(不算失败);IDE 未连接时跳过诊断检查。

### 范围门控(planStrictness)

批准后,AI 写文件时会检查目标是否在**当前阶段的 Files 白名单**内。通过项目 `.snow/settings.json` 的 `planStrictness` 配置:

| 值           | 行为                                             |
| ------------ | ------------------------------------------------ |
| `soft`(默认) | 计划外写入放行,但注入警告要求先 `amend` 修订计划 |
| `strict`     | 计划外写入直接阻断,必须先 `amend`                |
| `off`        | 不检查                                           |

`.snow/plan/**` 和 `.trellis/tasks/**` 目录始终允许写入。

### 批准前硬门控

批准前,AI 只能读代码/搜索/写计划文档,业务文件写入、终端命令、可写子代理全部被工具层拒绝——即使 YOLO 模式也无法绕过。

## 断点续跑

会话恢复(`/resume`)后,门控批准状态会从计划文件的 frontmatter 自动恢复,执行不中断。

如果检测到磁盘上有其他会话遗留的 `executing` 状态计划,新会话开启计划模式时 AI 会主动询问:**继续该计划**还是**开始新计划**。选择“继续该计划”会机器 adopt（重绑 session、恢复门控与范围）。也可显式调用 `plan-manage {action:"adopt"}`。

## 常见问题

**Q: AI 说"计划已批准"但工具仍被拦截?**
批准必须通过 `askuser-ask_question` 的明确选项(如 "Yes - Execute the entire plan"、"批准并执行"、"继续执行"),普通聊天回复不会解锁门控。

**Q: 批准被拒绝提示 missing_file?**
计划里引用了不存在的文件路径。修正路径,或给计划新建的文件加 `(new)` 标注。

**Q: 想临时改计划外的文件?**
让 AI 先调用 `plan-manage {action: "amend"}` 把文件加进计划(soft 模式下直接改也可以,但会收到警告)。

**Q: 活跃计划写在哪? 归档的计划在哪?**
活跃计划在 `.snow/plan/YYYY-MM-DD/[任务名].md`（创建日目录）；旧的顶层 `.snow/plan/*.md` 仍可被发现。归档在 `.snow/plan/archive/YYYY-MM-DD/`，按**归档日**分目录（可与创建日不同），重名自动加 `-2` 后缀。
