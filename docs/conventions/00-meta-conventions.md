# 00. 规范编写元准则与正典工程范式 (Meta Conventions & Canon Template)

> **定位**：定义 Snow 全仓工程（`snow-cli`、`snow-pty-test` 及扩展矩阵）中，所有约定规范（Conventions）文档的**写作模态、四大硬性结构、硬规范与软规范界限，以及启发/消融/反向消融思维推演范式**。
> **参照先例**：`skills-collection` SZ 规范基底、`IV8` 仓 `conventions/README.md` 与 `testing-scenario-tui`。
> **核心哲学**：**拒绝口号式空谈，拥抱公理级可验证性；硬规范必配自动化门禁，软规范提供正反模式对照；内外双向镜像对齐，历史序号单向递增。**

---

## 一、双目录镜像与版本同步契约 (Mirror Synchronization)

全仓存在两处物理约定的镜像挂载点：
1. **外层根目录规范**：`D:/dogepy/Tools/Snow/conventions/`
2. **内层应用规范**：`D:/dogepy/Tools/Snow/snow-cli/docs/conventions/`

### 强制执行铁律：
- **两端必须 100% 字节级一致**：新增、重命名或更新任何规范文档，必须同时原子提交至两处路径；
- **历史时间排序与序号前缀**：所有领域规范必须依据历史 Git 首发时间采用两位数字序号前缀（`00-`、`01-`、`02-`...），序号由 `00-meta` 起始递增；
- **登记即生效**：任何新设立的规范文档必须在两端的 `README.md` 索引总表中登记，未登记者视为孤儿无效草稿。

## 二、规范文档的四层黄金结构 (The 4-Pillar Canon Structure)

每一份归入 `conventions/` 的文档必须严格遵守以下四层结构：

```text
┌────────────────────────────────────────────────────────┐
│ 1. Frontmatter 元数据头 (dynamics, domain, status)    │
├────────────────────────────────────────────────────────┤
│ 2. 定位、参照先例与核心哲学 (Philosophy & Precedents)   │
├────────────────────────────────────────────────────────┤
│ 3. 架构分层、数学模型与正典规则 (Layering & Patterns)   │
├────────────────────────────────────────────────────────┤
│ 4. 启发式、消融性与反向消融审计 (Heuristics & Ablation)│
├────────────────────────────────────────────────────────┤
│ 5. 硬红线禁令与自动化门禁对照表 (Invariants & Guards)   │
└────────────────────────────────────────────────────────┘
```

### 1. Frontmatter 必填规范
```yaml
---
dynamics: [立,守,改,增]    # 动力学标签：立(新建)、守(基准防线)、改(重构)、增(补丁扩充)、废(弃用废弃)
domain: <领域标识>         # 核心领域：verify, meta, architecture, design-system, os, execution
status: normative         # 模态：normative (硬性强制验收标准) / descriptive (指引性建议)
---
```

## 三、硬规范（Hard Rules）与软规范（Soft Guidelines）的边界

| 规范类别 | 判定标准 | 实施载体 | 违规后果 |
| :--- | :--- | :--- | :--- |
| **硬规范 (Hard Rule / Invariant)** | 能够被形式化验证、静态分析（AST）或测试用例严格度量的物理指标 | 自动化测试门禁（`source/test/unit/core/*Guard.test.ts`）或 CI 构建流水线 | **PR 编译或测试直接飘红阻断，严禁合入主干** |
| **软规范 (Soft Guideline)** | 架构设计权衡、高内聚低耦合范式、重构演进时序、命名美学与代码优雅度 | 代码审查（Review）、设计评审（RFC）与正反模式对比清单（Do's & Don'ts） | 团队审查阻断，要求给出充分理由或优化方案 |

## 四、三维思维推演范式 (The 3D Audit Framework)

在推导或审查任何一项工程约定、架构调整与测试层级设计时，必须进行严格的三维推演：

### 1. 启发式探索 (Heuristics)
- **极值与边界探查**：思考在极端硬件（单核低频 CPU、Windows C/D 跨盘符、ANSI 宽度为 0、网络完全断开）下的系统不变量；
- **不变性契约**：无论外界发生何种故障，系统的核心状态（如会话文件、真实宿主环境、终端光标）必须保持绝对纯净。

### 2. 消融性分析 (Ablation)
- **“如果不做这项规范，系统会发生什么恶化？”**
  - 消融沙箱：业务代码散落写穿宿主，CI 并发测试互相污染；
  - 消融单斜杠 POSIX：Windows 路径反斜杠混入正则与 JSON 转义，跨平台解析灾难；
  - 消融依赖无环检查：模块间互相静态导入，冷启动时触发 TDZ 未定义运行时崩溃。

### 3. 反向消融推演 (Reverse Ablation)
- **“这项规范的成本边界与过度设计防范是什么？”**
  - 反向消融杜绝形式主义：规范只防真实存在并经过反例证伪的痛点，严禁为了规范而规范；
  - 最小必要性验证：每一个被提炼出的微内核或测试层级，必须能清晰回答“为什么现有机制无法解决它”；
  - **文风去形式化包装（Pragmatic Engineering Terminology）**：无论在规范正文、Issue 还是 PR 中，严禁使用夸大玄虚、大而无当的口号式包装词（如“全域降维打击”、“零容忍物理门禁网格”等）。必须坚持言简意赅、客观平实的工程表述（如统一采用“门控测试”、“检查流水线”、“路径规范”），突出实际交付的代码与测试事实。

## 五、规范生命周期与自审清单 (Convention Checklist)

新增或演进规范前，作者必须确认：
- [ ] 是否具备真实的错误反例（Anti-Pattern）与复现证据？
- [ ] 是否给出了正典实现范式（Canonical Pattern）？
- [ ] 是否明确定义了硬红线（Invariants）与自动化门禁？
- [ ] 是否在内外两处规范目录同步完成原子化落盘？
